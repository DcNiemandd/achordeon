## Profile

This is where the account is, and it is the only place in the app that is. What
an account is for, and what each tier gets, is its own chapter:
[Account](/settings-account/account.mdx).

You can manage your login and synchronization in this section:

- Login / logout, and adding a second sign-in method to the same account
- Buttons for Google Drive synchronization
- _Premium:_ switch for automatic sync
- Manual sync: back up the whole library to a file, or bring one back in

Sending a few songs to somebody else is a different job. That is
[export & import](/export-import/index.mdx), and it lives with the songs, because
choosing which songs is the whole act. Settings links there.

:::note[Drive access is asked separately]
Signing in with Google does not hand Achordeon your Drive. That permission is
asked the first time you back up to Google Drive, and it covers only the backup
file itself. See [your account & Google data](/settings-account/account-data.mdx#google-drive).
:::

## Application

- theme - system, light, dark, _FUTURE: colors_
- dark page - off unless you turn it on. With it on, every song the app draws goes
  light-on-dark while the app itself is dark: performing, watching, and the previews
  in Songs and Songbooks. The **Dark page** button overrides it where it appears:
  in the performing bar for that one performance, in the audience menu for that one
  viewing, and under the songbook pages for that book — the print preview says it is
  no longer showing the print output while it is dark. It is per device, and
  printing, PDFs, downloads and your audience are never touched by it
- language - EN, CS
- usage statistics - off unless you turn it on, and the same switch as the one on
  [Privacy](/privacy.mdx#extra-statistics)
- panel size - one size everywhere, or let each module remember how you sized its
  split view on its own

## Rendering

The renderer allows you to customize the output. There is global setting and scoped one.

[`Songs`](/songs/editing.mdx#renderer) scope. The controls are grouped into **Page**,
**Title**, **Fonts** and **Chords**:

- _Page_: scale (custom text size, useful for maximizing the page space), columns (for
  really long songs), aspect ratio, padding (the white border around the song), block gap
  (the air between a verse and a chorus — closing it up is often what fits a long song on
  one page, because with scale on Auto the room you take out comes back as bigger text),
  and where a song that doesn't fill the page sits, horizontal and vertical
- _Title_: position (on top of the page or sideways up the side) and layout (the subtitle
  stacked under the title or inline beside it)
- _Fonts_: the face the song itself is set in — lyrics, chords and labels — and the one
  the title and subtitle share. The title can be told to follow the song, which is what
  it does unless you say otherwise. Every choice is a font this device really carries,
  so what you see is what a PDF prints
- _Chords_: the same colour, size and notation a songbook can set, here for a single song

A few of those rows repay knowing how they behave:

- **Aspect ratio** — the picker has four shelves. _This device_ holds **Match this
  screen**, which measures the device you are holding and stores the ratio it
  measured, so a phone saves something like `131:284` and that keeps meaning _that
  phone_ after it syncs to the desktop; its sideways twin, **Match this screen,
  sideways**, is the same measurement turned over, which is how you get a landscape
  song without rotating a device that has rotation lock on. _Paper_ is A4 and Letter.
  _Portrait_ runs `9:19.5` down through `3:4` to square, _Landscape_ `21:9` down to
  `4:3`. Every named ratio carries its numbers in its label. Below the list is a
  free-text field: it takes a ratio like `3:4`, a fraction like `3/4`, a plain number
  or the word `A4`, and it turns away anything the renderer could not draw rather
  than storing a value that would quietly do nothing
- **Columns** are a count you set; the renderer chooses where to break. It only ever
  breaks between blocks, so a verse is never sawn in half, and it balances them so
  the tallest column comes out as short as it can. A song written as one long block
  has nowhere to break, so setting it to two columns changes nothing at all — a blank
  line is what gives the renderer a choice. Where the lines are long, two columns need
  twice the width and the fit scale is what pays for it, so the song comes out smaller
  rather than bigger
- **Padding** runs `0` to `4` in quarters, and like the block gap it is measured in
  text sizes rather than millimetres, so it holds its proportion however big the song
  is printed. `0` runs the song to the paper's edge
- **Content placement**, the two rows that say where a song sits, does nothing to a
  song that already fills its page: there is no leftover room to place
- **Chord size** costs height. A chord rides in a row of its own above the line it
  belongs to, and that row is as tall as the chords in it — so growing them makes the
  song taller, and the fit scale answers by drawing everything smaller

A single song can override anything. A songbook only carries the shared few below.

:::note[One song, one page]
The render settings exist to make the content fit one page.
:::

`Songbooks` scope:

- block gap - the air between blocks, set once for every song in the book
- chords color
- chords size
- chord notation - English (C, D, B) or German (H for B natural, B for B♭). It changes how chords are **printed**, but your song is left exactly as you wrote it, so switching back changes nothing else. `[H]` has always been understood as B natural whichever you pick, and English simply prints it as `B`, so a song that mixes the two spellings comes out in one language either way. The one thing that writes a spelling back into the text is a transpose, and it writes the song's own: in a German song, a chord that lands on B natural is written `[H]`. B flat is the exception and stays `Bb` in the text — a bare `B` in a file is B natural to every reader, so writing the printed spelling back would move the chord a semitone the next time the song was read. It prints as `B` all the same. The editor watches for the mismatch too: an `[H]` in a song set to English, or a `[B]` in one set to German, gets a wavy underline saying which name the page will print instead.
- song font - the face the songs themselves are set in. Set it on a songbook and every song in it follows.
- title font - the face the title and subtitle are set in: the song's own font, or any other. Set it on a songbook and every song in it follows.

## Font library

Settings ▸ Font library lists every font this device can set a song in — the ones
Achordeon ships with, and any you add yourself.

**Add a font** searches Google Fonts by name — pick a result and it is added — and also
takes a `.ttf` file, or a link. The link can be the embed address Google
Fonts hands you, or a direct `.ttf` address on jsDelivr or raw.githubusercontent.com.
Whichever way, the font is **downloaded once and kept on the device**, so it works offline
from then on and nothing is fetched while you are reading a song.

The search reads an index of the Google Fonts catalogue that ships with the app rather
than asking Google, so the list narrows as you type and there is no Search button. Two
letters is the shortest query it answers — below that a search matches most of the
catalogue and means nothing. Under each name is what installing it will give you, counted
out of the four styles a song can ask for — `4 of 4 styles`, `2 of 4 styles` — and worded
exactly as the library row will word it afterwards. If the index itself cannot be read,
the dialog says so where the results would be, and the other two ways in still work.

Some things worth knowing:

- **One file is one style.** Adding the regular does not add the bold — add that as a
  second file. A style you never add is borrowed from another font, and Settings says
  which one; you can change where it is borrowed from.
- **A variable font counts as one style**, its default instance. One variable file
  carries a whole range of weights and a browser can draw any of them, but a PDF cannot,
  and Achordeon will not show you on screen what it cannot print. The row says so, rather
  than leaving the count looking like a failed download — which is why a family
  advertising nine weights on the Google Fonts site can land here as a single style.
- **Where a missing style is borrowed from** is a row of its own, the third in the render
  settings' **Fonts** group. It starts on Roboto Mono, the face the app itself is set in,
  which has all four styles and is on the device already, and only a font that is missing
  no style can lend. While the song's own font is missing nothing the row is greyed out
  rather than hidden, so choosing a font never makes the panel jump under your pointer.
  The reason it exists: without a donor, italic text would slant on screen and come out
  upright in a PDF — a browser fakes a slant out of the regular, and a PDF has no such
  trick.
- **An embed link is read for its query string only.** That string is the list of
  families you picked on the Google Fonts site, so a link naming four families adds all
  four.
- **A font stays on the device you added it to.** It travels in a [backup](#backup),
  because that is your whole library. It does **not** travel in an
  [export](/export-import/index.mdx): that file names the fonts your songs use so the person
  opening it knows what to install, and never carries the font itself.
- **Removing a font is safe.** Songs set in it go back to the default and come back to
  it the moment you add it again.
- **TrueType only.** `.otf` files are turned away, because half of them hold outlines a
  PDF could not print — and a font that looked right on screen and came out wrong in
  print is the one failure worth refusing up front.
- **The four Achordeon ships with cover the Latin alphabets.** They are cut back to
  those to keep the download small, so a song written in Russian or Greek prints empty
  boxes. Add a font that has those letters and it will print them.

## Backup

Save your whole library, and bring it back later. This is the entire database, not a selection, different from [exporting](/export-import/index.mdx) a few songs to share.

A backup can live in either of two places, and they are the same backup:

- **a file** you keep wherever you keep files
- **your Google Drive**, if you would rather not hold the file yourself

Bringing one back asks what it should do, because a backup serves two jobs:

- **Add to my library** - the backup's songs and songbooks land beside yours. Where you have both, the newer one wins. Your settings are left alone.
- **Replace everything** - the library goes back exactly as the backup has it. Anything not in the backup is lost, your settings included.

The question is the same whether the backup came from a file or from Drive, and so is the answer.

:::note[Add is the one you usually want]
Replace is for putting a machine back the way it was. If you are after songs from an old backup, Add gets them without touching anything you have written since.
:::

:::note[Backup is not sync]
Sync keeps one library the same on every device you sign in on, continuously, with no file involved. A backup is a copy you make and choose when to bring back. Sync will faithfully copy a deletion to your other devices. A backup is what still has the song afterwards.
:::
